Project One

Automated Faceless TikTok Generator

A Python program running entirely on a local machine that writes, voices, times, and edits short videos, then measures their audience retention to improve future stories.

Short-form vertical video platforms like TikTok feature a popular genre: "faceless storytime" videos. These typically pair a gripping, strange, or absurd first-person narrative with synthetic speech, bold animated word-by-word subtitles, and mesmerizing background gameplay footage. Producing these videos manually is labor-intensive: coming up with ideas, editing the text, recording audio, synchronizing subtitles word by word, cutting footage, and reviewing analytics to figure out why viewers lost interest.

This project automates that entire lifecycle into a single pipeline. Crucially, the entire stack runs locally on my Apple Mac without recurring cloud API fees, using open-weight models for text generation, speech synthesis, and audio alignment.

The End-to-End Pipeline

A single CLI command triggers an automated six-stage workflow that takes an idea from zero to a ready-to-post 1080×1920 video:

1. Pick Strategy → 2. Pitch & Write → 3. Voice Synthesis → 4. Word Alignment → 5. Video Assembly → 6. Learnings Loop

Stage 1 · Strategy & Exploration

Hypothesis Selection

Before generating anything, the program selects a testing profile: one category (such as unhinged neighbor, absurd petty revenge, or bizarre workplace chaos), one hook format (such as a direct provocative question, a shocking factual statement, an intriguing opening like "I never told anyone...", or a chaotic mid-action start), and one synthetic voice profile. These variables are recorded into structured metadata for every video, allowing statistical comparison across hundreds of posts.

Stage 2 · Multi-Pass Story Generation

Idea Pitching, Selection, and Script Polish

Instead of relying on a single prompt, the local large language model (Qwen 27B running locally via LM Studio) operates across multiple distinct passes:

  • Pitching 5 ideas: The model generates five radically different story concepts, each with a clear premise, an opening hook under 15 words, and a concluding twist.
  • Editorial evaluation: Running in an "editorial" role, the model evaluates all five ideas against strict retention criteria (Is the hook irresistible? Is the premise absurd yet delivered deadpan? Can it escalate naturally for 80 seconds?) and selects the single strongest pitch.
  • Full script creation: The selected idea is written into a complete 330–400 word script designed for an exact speaking duration between 75 and 85 seconds.
  • Revision & Tightening: A separate revision prompt cuts unnecessary middle segments, accelerates the escalation, and sharpens the final twist to encourage comments and debate.

Every story prompt dynamically injects all accumulated rules from Learnings.md as well as all previously used titles, preventing repetition and actively reinforcing what worked in past videos.

Stage 3 · High-Fidelity Voice Synthesis

Neural Speech Generation

The script is rendered using Kokoro, a lightweight local neural text-to-speech engine. The synthesized audio is saved as uncompressed WAV. Because TikTok watch-time algorithms heavily reward content over 60 seconds that maintains high completion rates, the system verifies the exact duration: if the synthesized speech falls below the minimum target duration, the script is dynamically expanded with additional narrative escalations and re-synthesized until it hits the target window.

Stage 4 · Speech Recognition & Forced Alignment

Millisecond Word-Level Timestamps

To display high-energy, animated on-screen captions, every single word needs an exact start and end timestamp. The program runs faster-whisper locally over the synthesized voice file. Because raw speech recognition can mishear words or alter punctuation, the system runs a sequence-matching alignment algorithm (using diff opcode matching) that locks Whisper's detected timestamps onto the original, perfectly spelled script text.

The aligned words are compiled into an Advanced SubStation Alpha (.ass) subtitle track. Words are grouped into brief 1-to-3 word display chunks, rendered in prominent bold typography with heavy dark outlines, an energetic scale-pop animation on appearance, and vivid color highlighting on the exact active word currently being spoken.

Stage 5 · Video Assembly & Rendering

FFmpeg Compositing

Video rendering is executed through an automated FFmpeg pipeline:

  • It inspects a high-resolution, long-duration gameplay recording (such as Minecraft parkour) and chooses a random starting point long enough to cover the audio plus a brief breathing tail.
  • It crops the 16:9 gameplay to a 9:16 aspect ratio (1080×1920), scales with a Lanczos filter, applies a subtle unsharp mask for crisp mobile viewing, and burns in the styled ASS subtitles.
  • The vocal track is mixed and encoded using AAC audio, while the video is encoded using hardware or software H.264 with high-profile fast-start flags for immediate playback on mobile devices.

Stage 6 · Feedback Loop & Autonomous Learning

Retention Analysis and Continuous Improvement

Once a video is published, actual viewer metrics (total views, average watch time, full completion rate, and the exact drop-off second from the retention curve) are recorded back into an Obsidian vault markdown note.

When running the analysis engine, the language model reads the video's script, word timestamps, and channel averages. By mapping the drop-off second to the exact sentence spoken at that moment, the AI diagnoses precisely why audience retention dipped (for example: a pause that was too long, an escalation that lost plausibility, or a confusing transition). It synthesizes these findings across all posted videos into a living rulebook: rules supported by multiple videos become permanent editorial guidelines, while single-video patterns remain tentative until verified over 10+ posts.

Project Two

FaceLook Hero Mode: How I Reached the Leaderboard

A lightweight browser-based automation script that solved an educational face-recognition game with near-perfect accuracy and sub-millisecond reaction speeds.

1. The Premise of the Game

FaceLook is a school web application designed to help students and faculty learn each other's names and faces. In Hero Mode, players face an endurance test of hundreds of consecutive questions under time and health constraints:

  • Name Round: The game displays a target person's name and four face photographs. The player must select the matching photo.
  • Face Round: The game shows one large photograph and four candidate names. The player must select the correct name.
  • Health & Streaks: Correct answers increase the streak multiplier and restore health; incorrect answers or hesitation deplete health until game over. Top leaderboard placement requires high streaks across hundreds of questions without missing.

2. The Underlying Architectural Vulnerability

During manual play, inspecting the page source and network traffic revealed a critical design shortcut: every face image file on the server was named directly after the person pictured (for example, First_Last_ClassYear_RandomHash.png).

Because the image URL itself held the plaintext answer, solving the round did not require complex facial recognition or computer vision models. It was fundamentally an algorithmic text-matching challenge between the on-screen prompt and the image filename attributes already present in the DOM.

3. How the Bot Worked in Practice

The bot was designed as a lightweight console script pasted directly into the browser's developer tools on the active game page. Its internal architecture solved three key challenges:

DOM Mutation Monitoring

Rather than relying on blind polling or fixed interval timers, the bot configured a MutationObserver paired with requestAnimationFrame. It continuously monitored changes to image sources, button classes, and text elements, reacting the very millisecond a new question rendered.

Delay Collapsing ("Turbo Mode")

The game normally enforced an artificial ~300ms pause between questions. The bot monkey-patched window.setTimeout, detecting transitions between 200ms and 500ms and immediately executing them at 0ms. This made questions appear continuously without waiting.

Exact Name Normalization

To prevent false positives (such as "Ben" incorrectly matching "Benjamin"), strings were stripped of accents, diacritics, punctuation, and honorifics (Mr., Ms., Dr.), and compared using strict multi-token key sets.

Handling Real-World Exceptions

The bot maintained an override dictionary for school-specific nicknames (where a student's file name said "John" but the game displayed "Peter"), accounted for faculty staff titles, and handled special pet rounds.

4. Overcoming High-Speed Race Conditions

Under turbo speed, a subtle race condition emerged: the game's client-side framework frequently updated the text prompt one frame before updating the four image source URLs. If the bot clicked instantly on text change, it would occasionally click based on an outdated image from the previous question, breaking the streak.

To resolve this, a frame-stabilization gate was implemented: the script generated a unique signature combining the current prompt and all option image URLs, requiring this signature to remain completely stable across two consecutive animation frames before authorizing a click. This eliminated race condition errors completely while retaining maximum game speed.

5. Leaderboard Submission

The automation strictly restricted its operation to answering the in-game questions. Once the endurance run concluded, the game presented its standard score submission screen. The player entered their display name manually and submitted the legitimate high score to the public leaderboard.

Responsible Disclosure

Security Finding: Unauthenticated Photo Directory

While building the automation, an inspection of the client application revealed that the entire database of student and teacher photographs was completely accessible to anyone on the internet without a password.

The Discovery

In web applications handling sensitive internal directory data, access to personal photographs and rosters should require active student or faculty authentication. While examining the asset loading sequence for FaceLook, I discovered that the frontend loaded an unauthenticated JavaScript utility file containing an index of all asset categories, class rosters, and relative image paths.

Using these paths, any external user could query the file server directly and download high-resolution photographs of every single enrolled student and faculty member, complete with their first name, last name, graduation year, and assigned status — without entering any credentials, session tokens, or school passwords.

Verification via Batch Ingestion

To understand the scope of the exposure, a verification script was developed. The script performed the following steps:

  1. Manifest Extraction: Fetched the public JavaScript manifest file and parsed all referenced image file paths using regular expressions.
  2. Concurrent Download: Initialized a multi-threaded request pool to test whether individual asset URLs enforced any authentication, CORS boundaries, or IP-based rate limiting.
  3. Storage & Audit: Verified that hundreds of megabytes of personal identity photos could be harvested directly across all grades, faculty departments, and school years.

Ethical Responsibility & Resolution

Building a high-score game bot is a harmless exploration of frontend logic. However, discovering that an entire school directory's biometric and identity photographs are exposed without authentication is a serious privacy and safety concern. Rather than sharing or misusing the collected data, the entire vulnerability — including the mechanism of the exposure and remediation steps — was documented responsibly so the school administration could secure the image storage behind proper role-based authentication.

Projects documentation prepared for review. Both systems represent explorations of software automation, web reverse-engineering, and ethical security analysis.
